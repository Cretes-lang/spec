## Proposed decision and rationale

**A deliberately synchronous native core built only after architecture acceptance and subsequent syntax specification.**

The proposal selects a Rust-hosted modular frontend, handwritten recursive-descent statement/declaration parsing with a precedence-oriented expression parser, typed HIR, ownership-aware MIR and an LLVM native adapter. The parser strategy is an implementation direction; it does not select token spellings, operators, precedence or grammar. Error recovery must preserve token progress and source spans.

The initial target is Linux x86-64, pending target conformance. Core values include fixed-width numbers, booleans, Unicode scalars, text, bytes, tuples, nominal aggregates and tagged sums. Functions, lexical scopes, branching and iteration lower to explicit control flow. Evaluate operands and function arguments left-to-right; short-circuit boolean operations evaluate the right side only when required. Source declaration order does not cause import-time execution. Exact entry-point declaration is syntax work; the driver invokes one selected entry target, converts its result to an exit status and distinguishes runtime faults.

Text is valid UTF-8 and never conflated with arbitrary byte buffers. Text operations document byte versus scalar boundaries; slicing must preserve validity or operate on bytes explicitly. Core collections are a contiguous growable sequence, map and set with documented complexity and allocation costs. Built-in type constructors support these and option/result while user-defined generics remain excluded. Maps use randomized collision-resistant hashing and document iteration order; ordered output is explicit.

v0.1 standard library: own standard streams, files, paths, raw arguments, environment reads, clocks, text/bytes, core collections and structured errors. File operations include the Phase 1 subset; recursive traversal, processes, network protocols, concurrency, user FFI/unsafe, multidimensional tensors, remote packages and advanced tooling remain excluded. Architecture documents for these later facilities prevent incompatible foundations; they do not enlarge v0.1.

Implementation sequence after approval: source/diagnostics and grammar; typed frontend and module graph; ownership/cleanup MIR; core runtime/platform boundary; backend/linker; v0.1 library/CLI; conformance, fuzzing, target and release validation. Each step must link the original requirement IDs. The authoritative 86-entry scope stays in ../requirements/V0.1-REQUIREMENTS.md.

Conceptual flow: original source snapshot → tokens/recoverable AST → resolution/typed HIR → ownership and initialization analysis → verified MIR with checks/cleanup → conservative optimization → LLVM IR/object → system linker plus matching core runtime → native artifact. `check` exits before backend work.

## Options, advantages, disadvantages and rejected alternatives

Adding network/async/FFI/tensor implementations now was rejected as milestone expansion. A throwaway untyped frontend was rejected because v0.1 already requires safety. One minimal end-to-end native core is proposed, with no production code in Phase 2.

Doing nothing leaves the linked architecture questions unresolved and prevents a coherent implementation plan. This proposal is a review candidate, not an accepted language rule.

## Security, performance, developer experience and implementation impact

Security: trusted runtime/backend still require review and fuzzing. Performance: record baselines rather than invent targets. DX: single-file run and precise diagnostics are first-release deliverables. Implementation: full 86-entry v0.1 traceability is required; architecture coverage is not conformance.

## Future verification

Later run positive/negative conformance under both profiles, malformed-source fuzzing, numeric boundaries, ownership/cleanup, Unicode, file failure, CLI behavior, target installation and release integrity.

## Risks and open questions

Phase 2 cannot close until RFC acceptance, especially SAFE-023. Phase 3 must then specify grammar/notation and fill formal semantic details before production implementation.

Cross-cutting risk owners and closure evidence are in [RISKS.md](RISKS.md). Acceptance requires the [RFC process](https://github.com/Cretes-lang/rfcs); publication or merge of this explicitly proposed document is not acceptance.
