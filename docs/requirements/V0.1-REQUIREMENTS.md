# Cretes v0.1 requirements

> **Status:** Phase 1 requirements baseline · **Defines language semantics:** No · **Last reviewed:** 2026-09-27

This document defines the **minimum useful first language milestone**, Cretes v0.1. It lists every requirement whose target is `v0.1`, states how much of each applies at v0.1, and defines exit criteria.

> **Nothing here is implemented.** These are requirements for future implementation, after Phase 2 architecture decisions and the approval of syntax and semantics through RFCs. [VERSIONING.md](https://github.com/Cretes-lang/.github/blob/main/VERSIONING.md) describes `0.1.x` as "usable development" releases. No date is implied.

## Purpose of v0.1

v0.1 proves that Cretes' core language design works end to end. A developer should be able to:

1. write a program in one or more `.cretes` files;
2. check it with clear diagnostics;
3. build and run it on at least one Tier 1 candidate platform;
4. use text, collections, files, standard streams, arguments and environment variables;
5. rely on the language's safety guarantees for everything they write.

v0.1 is **not** intended to be production-ready, stable or feature-complete for any of the four domains. It is the foundation that the domain milestones build on.

## What v0.1 contains

| Area | Contents | Requirements |
| --- | --- | --- |
| Core language | `.cretes` source files, UTF-8 lexical structure, primitive values, bindings, expressions, functions, control flow, loops, modules, user-defined data types, basic type checking, error handling | CORE-001 to CORE-027 (v0.1 subset), NET-001, AI-001 |
| Safety | No undefined behavior in safe code, memory, null, initialization and integer safety, deterministic resource release, defined faults | SAFE-001 to SAFE-011, SAFE-013, SAFE-015, SAFE-020, SAFE-021, SEC-001 |
| Basic standard library | Text, core collections, basic I/O, files, paths, arguments, environment, clocks, structured errors | CORE-024, CORE-032, CORE-033, AUTO-006, AUTO-008, AUTO-012 to AUTO-014, AUTO-019, AUTO-025, AI-005, SEC-008 |
| Toolchain | `cretes run`, `cretes build`, `cretes check`, single-file programs, manifest for multi-module projects | DX-001 to DX-004, AUTO-001, CORE-028 |
| Quality | Diagnostics, compiler and language tests, fuzzed front end, basic documentation, release integrity | DX-005 to DX-008, DX-018, DX-019, CORE-031, SEC-032 |
| Policy | Platform support policy, ABI policy, performance-claim policy | PLAT-001, PLAT-005, PLAT-010, PLAT-011, INTOP-018, PERF-017 |

## What v0.1 deliberately excludes

The following are **not** required in v0.1. The v0.1 architecture must still leave room for them (see [Architecture obligations](#architecture-obligations-beyond-v01)).

- **Concurrency:** tasks, async I/O, channels, parallelism ([CONCURRENCY.md](CONCURRENCY.md)).
- **Networking:** sockets, DNS, TLS, HTTP, WebSockets ([networking.md](domains/networking.md)). The only exception is the byte types of NET-001.
- **Process management:** spawning and supervising child processes (AUTO-009 to AUTO-011).
- **AI/ML facilities:** n-dimensional arrays, SIMD, inference integration ([ai-ml.md](domains/ai-ml.md)). The only exceptions are AI-001 and AI-005.
- **Cryptography and TLS** ([cybersecurity.md](domains/cybersecurity.md), Part B). The only exception is SEC-008.
- **User-visible FFI and unsafe code** ([INTEROPERABILITY.md](INTEROPERABILITY.md)).
- **User-defined parametric types** (CORE-019). Built-in collections suffice for v0.1.
- **Formatter, linter, test runner, language server, debugger integration, documentation generator** (DX-009 to DX-014).
- **Package manager and registry** (DX-015). Multi-module projects are built from local sources only.
- **JSON, serialization, logging, HTTP clients, archives.**

## Exit criteria

v0.1 may be released as a prerelease once all of the following are true:

1. Every MUST requirement above is satisfied to its stated v0.1 extent, with the verification approach named in the requirement.
2. Every SHOULD requirement above is satisfied, or its deviation is documented in the release notes.
3. The specification describes every v0.1 language feature and marks each as experimental ([CORE-031](CORE.md#core-031--specification-coverage-of-shipped-features)).
4. Positive and negative conformance tests exist for every v0.1 language feature and pass on every platform claimed as supported.
5. Compiler front-end fuzzing has run without unresolved crash findings ([DX-008](CORE.md#dx-008--robustness-on-malformed-input)).
6. At least one Tier 1 candidate platform meets [PLAT-005](PLATFORMS.md#plat-005--criteria-for-official-support).
7. Release artifacts, checksums, known limitations and documentation meet [VERSIONING.md](https://github.com/Cretes-lang/.github/blob/main/VERSIONING.md), [DX-018](CORE.md#dx-018--release-documentation) and [SEC-032](domains/cybersecurity.md#sec-032--toolchain-release-integrity).
8. Startup, check and build timings are measured and published as baselines ([PERF-004](PERFORMANCE.md#perf-004--program-startup-latency), [PERF-005](PERFORMANCE.md#perf-005--toolchain-responsiveness), [PERF-006](PERFORMANCE.md#perf-006--analysis-faster-than-full-builds)), with no comparative claims ([PERF-017](PERFORMANCE.md#perf-017--evidence-before-claims)).

| Networking | [NET-002](domains/networking.md#net-002--scalable-asynchronous-io), [NET-013](domains/networking.md#net-013--backpressure) |
| FFI and unsafe code | [SAFE-016](SAFETY.md#safe-016--explicit-and-auditable-unsafe-code), [INTOP-001](INTEROPERABILITY.md#intop-001--calling-c-abi-functions), [INTOP-005](INTEROPERABILITY.md#intop-005--memory-ownership-across-the-boundary) |
