# Cretes v0.1 syntax freeze candidate

**0.1 Draft — proposed, unaccepted, unimplemented; not frozen.**

The [specification](SPEC.md) and [token grammar](cretes.ebnf) form the candidate source-language target, alongside [lexical definitions](lexical.ebnf). The original [86 requirements](../requirements/V0.1-REQUIREMENTS.md) retain their priorities and scope. Candidate syntax does not establish implementation conformance.

## Included candidate surface

Strict UTF-8 `.cretes`; explicit security/identifier rules; comments; fixed-width numbers, text/bytes/scalars; tuples; named records and tagged sums; initialized let/var/const; explicit annotated functions and entry contracts; calls and fixed operator tiers; braces and semicolons; if/while/for/loop/match; qualified imports and pub visibility; compiler-known collection/Option/Result/Box type constructors; explicit borrows with returned-reference provenance; Result propagation; deterministic normal cleanup; canonical formatting and diagnostics requirements.

Every included construct is V0.1 REQUIRED within this syntax candidate. No V0.1 OPTIONAL syntax has been selected. The grammar recognizer is EXPERIMENTAL tooling, never a shipped language feature. Methods/attributes are DEFERRED; user generics/interfaces, function values/closures, async/concurrency, FFI and user unsafe are POST-V0.1. Their current absence does not erase later requirements.

## Intentionally absent

Inheritance, operator overloading, macros, reflection, compile-time user execution, metaprogramming, decorators, effects, specialization, implicit numeric conversions, nullable references, unwinding, arbitrary top-level effects, range syntax, wildcard imports, implicit tail returns, user destructors, borrowed aggregate fields, partial field moves and multi-source borrowed returns.

Several restrictions deliberately keep the first checker tractable. Extensions require a reasoned RFC and fixtures, not an undocumented parser convenience. Standard-library APIs and manifest serialization remain separate specifications. Their absence must not be filled by arbitrary implementation choices in Phase 4.

## Implementation handoff after acceptance

The source manager must retain bytes and stable spans; lexer emits six lexical categories plus exact keyword/operator terminals; parser consumes the program rule and produces source-preserving item/type/statement/expression/pattern structures. Semantic passes must enforce name/visibility/arity, constants, result handling, exhaustive matches, return completeness, move/loan/provenance and cleanup. The 16 semantic-negative fixtures are starting obligations for those future passes, not a completed conformance suite.

No AST schema or production parser is implemented here. Grammar recognition demonstrates syntax only. Before a safe-code claim, formal ownership rules and implementation tests need further expert scrutiny. Before multi-module builds, resolve the existing manifest format gate (Phase 2 R-11). Before a release, complete the full v0.1 requirement tests and target/release gates.
